    软件架构与分层

    概述：¶

    前情提及到JZW7258架构分IDK和AVDK，前者作为硬件驱动接口，支持更改引脚配置及相关驱动工作等；后者作为LCD显示，支持在LCD上draw用户想要的样式等。AVDK向上兼容IDK，两者使用时不必过度区分，用户只需注意调度关系即可。

    JZW7258软件层分为中间件层(Middleware)，组件层(Components)，应用层(projets目录下)。其中，中间件层和组件层共同组成API接口函数，用户逻辑开发皆在应用层完成，调用API即可，无需过多关注底层实现逻辑。

    组件层作为连接中间层和应用层的重要环节，基于FreeRtos系统为用户提供软件设计平台，已为每一个模块封装好线程安全。

    中间层抽象了硬件及上层应用，方便用户在不同方案中切换，譬如SOC选择(工程默认BK7258)、各个外设选择。

    应用层作为用户直接使用的部分，包含了如何编译程序、工程配置等功能，从projects目录下的CMakeList文件作为构建方案入口。

    构建与配置：¶

    概念：¶

    • projects下的每个文件都是一个可编译工程，包含了配置文件config、主文件main。
    • 配置文件为构建目录下生成的sdkconfig.h文件，在成功编译某个工程后生成的build中，根据用户工程下的配置文件而生成。
    • 用户开发中，需要引用组件层的API或某个文件时，需要在CMakeList文件中包含对应文件名及其相对路径。

    新建工程：¶

    具体可参考SDK中projects目录下的文件，已为用户设计案例为jzw7258文件，将以此例程为例说明。其中包含了LCD显示内容，以及开发板外设工作。为用户模块化设计及测试程序运行，提供模块化开发。对于开发板外设工作，可在bk_idk架构中开发，由于外设驱动都在这一层，无需向上引用，模块化时非常方便，也可向下在AVDK里直接引用。同样，对于LCD显示的模块化测试，需要在根目录下的工程中完成，且只能在这层调用，不可向上的IDK引用。简而言之，用户的应用逻辑实现在AVDK目录下的工程，AVDK可调取IDK的接口，反之不可实现。此外，组件层可配置、新添LCD和TP参数，应用层工程里选择对应name及分辨率即可。

    当新建工程时，通过例程的根目录下CMakeList文件作为编译入口，需要确认编译工具链的路径，编译时的工程名，以及需要引用的组件层的文件。 而后关注main主文件下的CMakeList文件，这个文件区别于前者，在于这里真正需要引用的内部文件需要参与编译运行的。

    • 首先确认的是注册函数，将组件层需要的文件名包含进来，src和inc默认包含例程里所有存在的.c和.h文件，PRIV_REQUIRES包含的是组件层和中间层的文件名，比如这里的bk_init，通过全局搜索，找到此文件位于/bk_idk/components/,bk_init中包含对应.c和.h文件，以及当前文件的CMakeList。不难发现，SDK中每层文件都含有属于本文件的CMakeList文件，含有向上包含的功能也有向下被引用的封装，将每一层分离开来，这样的模块化设计便于用户开发。 plantuml $armino_component_register{ SRCS "${srcs}" INCLUDE_DIRS "${incs}" PRIV_REQUIRES bk_init bk_cli }

    屏幕显示¶

    上述内容简介了LVGL烧录的UI界面，适配LCD硬件驱动，接下来从软件角度详述屏幕渲染显示的原理。 在LVGL事件中断函数里，详细描述了LVGL的渲染过程，首先确认渲染内存大小为显示内存的十分之一（Xyes * Yyes * color(bit) * 8BYTE / 1024 /10），采用双BUF缓存方式。配置好参数初始化LV硬件接口层，启动LV。至此算LVGL渲染的初始化部分，现在可以正式向里面draw用户所需要的UI了：打开锁，填充内容，关闭锁，启动，向CPU0传递数据。开锁关锁是为保护LV渲染，不被线程其它事情干扰。

    提示

    LVGL需要一个缓冲区在此绘制各个部件，通过这个缓冲区传递给显示驱动程序的"flush_cb"，复制内容到显示器，每次渲染至少一行。 有三种缓冲配置：一个缓冲区；两个缓冲区（从第一个缓冲区发送到第二个缓冲区时，绘制屏幕的下部分，使其渲染和刷新同时进行）；双缓冲（两个大小相同的缓冲区，并将disp_drv.full_refresh设置为1，即代表一直更新，LVGL始终在flush_cb中渲染整个屏幕，只需改变帧缓冲的地址即可）。

    一路跳转，LVGL这层中断服务函数，位于mutilmedia这个组件层中，封装在了FreeRTOS创建的一个名为"media_major_mailbox_thread"线程中，其优先级为4，栈空间为2048Bytes。这就需要用户在开发过程中注意以下两点

    警告

    注意优先级，会被高优先级的任务而打断； 注意空间大小，会溢出。

    再次回到主函数中，除了LVGL中断服务函数，还有一个ipc中断服务函数，运行在CPU1中，同样做了对LV的渲染工作，并被media_ipc_chan_cfg_t结构体中的回调函数所调用了，在media_ipc_channel_open里被调用，代表打开LCD。

    media_ipc_lvgl_callback是实现多核协同渲染的核心通信机制，主要作用跨核通信，对此实现的方式是硬件加速的IPC通道+内存共享+中断协同三级架构实现。

    LVGL¶

    由于BK7258多媒体执行在CPU1上，lvgl的执行需要在CPU0上先启动CPU1，然后发送mailbox消息到CPU1上执行相关代码，最后在CPU1上执行完成后返回执行状态。在CPU0上调用media_app_lvgl_open()，并启动CPU1,发送LVGL event消息，在CPU1上定义lvgl_event_handle(于上文中提到的LVGL配置及渲染部分)，操作LCD打开与LVGL启动，最后将数据通过CPU1发送到CPU0。

    参数配置说明

    • LVGL中使用SRAM作为运行内存，其中draw_buffer的内存有两种选择，可通过宏 CONFIG_LVGL_USE_PSRAM 来设置draw_buffer使用psram内存还是sram内存，使用sram内存时的帧率会比使用psram内存时的帧率高。默认不打开宏。
    • LVGL的draw_buffer在选择使用sram内存时，其大小根据官方的推荐为十分之一屏幕大小的size，可以在不损失帧率的情况下节省内存，以字节为单位。
    • 参数draw_pixel_size根据draw_buffer的大小进行设置，以像素为单位。
    • 关于双draw_buffer和双frame_buffer，双draw_buffer主要是为了并行绘制来提升显示帧率，但会消耗更多的sram内存，双frame_buffer主要是为了解决显示撕裂问题，在无触摸滑动交互的情况下可不使用双frame_buffer，具体情况可自行选择。
    • 参数lcd_hor_res和lcd_ver_res分别为LCD分辨率的宽和高。
    • 参数rotation可传入不同的值实现不旋转、旋转90度、旋转180度和旋转270度。LV适配了硬件接口层，改变LV的旋转角度即改变了硬件的旋转，无需对硬件再次进行旋转，且同时旋转了TP，硬件确保TP和LCD起始坐标位置一致即可。
    • TP打开接口中的最后一个参数用于解决触摸坐标和实际坐标是否存在镜像关系的问题。

    FreeRTOS¶

    jzw7258基于FreeRTOS实时操作系统工作，对物联网设备和多媒体进行统一管理，保护程序安全。其功能包括：任务管理、时间管理、信号量、消息队列、内存管理、记录功能、软件定时器、协程等，可基本满足较小系统的需要。SDK中已完成对FreeRTOS的移植，且已完整融合进了SDK中，并提前创建了各模块的线程。

    一个FreeRTOS主要由BSP、内核、组件组成，内核包含多任务调度、内存管理、任务间通信的功能，组件包含网络协议、外设支持。由于FreeRTOS是可裁剪的，且对内存空间要求非常严格，这也使得FreeRTOS核心代码只要9000行左右。SDK对FreeRTOS路径位于bk_idk/components/os_source/freertos_v10.

    FreeRTOS内核同时支持轮换调度算法，系统允许不同的任务使用相同的优先级，在没有更高优先级任务就绪的情况下，同一优先级的任务共享CPU的使用时间。

    多核处理SMP架构¶

    SMP涉及多核处理系统，FreeRTOS smp代码路径位于bk_idk/components/os_source/freertos_smp. SMP全称Symmetric Multiprocessing，即多处理器系统：多个处理器核心组成的计算机系统，每个处理器核心都能独立工作，包括执行任务和运行程序。SMP系统中以 对称性和共享内存 为特点著称，所以处理器核心都具有对此的地位，能够执行相同的任务、访问相同的资源，并通过相同的内存空间互相通信，使通信更加方便，但同时也需要注意安全性，对其做相应处理防止线程之间存在竞争状态。

    SMP核心优势就是，多处理器核心同时执行任务，互相通信。这样在程序运行中能够分担负载，有效加速响应。

    默认app工程是AMP架构

    SMP在FreeRTOS中应用¶

    • 创建线程，调用创建线程接口，设置包括到指定CPU、线程名、优先级、栈空间大小等参数。回顾上一节LVGL提到的创建线程为例，在组件层中的多媒体管理中，创建线程包含LVGL处理。
    bk_err_t rtos_create_thread_with_affinity( beken_thread_t *thread,
                                            uint32_t affinity,
                                            uint8_t priority,
                                            const char* name,
                                            beken_thread_function_t function,
                                            uint32_t stack_size,
                                            beken_thread_arg_t arg );

    以上代表创建具有亲和性的新线程，亲和性代表第二个参数，即指定到某一个CPU，为-1表示所有核心。而上述LVGL创建的线程，封装了此API，并指定到CPU1。可通过代码中具体实现比较各个创建线程方式的使用。

    • 初始化FIFO队列，同其它组件一样，线程也需要初始化，如下是此API函数定义，参数包括指向需要初始化队列的指针，队列名称，队列中对象的字节大小，及队列深度。
    bk_err_t rtos_init_queue( beken_queue_t* queue, const char* name, uint32_t message_size, uint32_t number_of_messages )
{
    __maybe_unused_var(name);

    if ( ( *queue = xQueueCreate( number_of_messages, message_size ) ) == NULL )
    {
        return kGeneralErr;
    }

    return kNoErr;
}

    在上述创建LVGL线程前，同样需要初始化LVGL队列，LVGL队列深度为20，即队列里最多20个对象。在初始化队列和创建对象的返回值是同一个局部变量，最终作为media_ui_task_init()函数返回值返回，并包含了异常处理。

    ret = rtos_init_queue(&media_ui_msg_que,
                                "media_ui_msg_que",
                                sizeof(media_msg_t),
                                20);

    LVGL线程初始化和其它LCD、UV多媒体初始化在一层初始化中，又包含于media_major_mailbox_message_handle()中，创建了一个优先级为4的线程，不指向CPU，这就意味着指向了每一个CPU。

    从LVGL中断函数出发，一直向上寻找接口，发现他们的父级是media_service_init()接口，这个接口在主函数中，未规定在某个CPU中，即代表中间层的初始化在每个CPU都有作用。
